Chapter 1 of 8

One author, one language: a second version is a cheap way to catch mistakes

All the numbers on this site come from Python code. If that code has a slip in a unit, an index or the solver set-up, every chart would carry the same slip. So the key parts were written again from scratch in MATLAB R2024b, and the two were compared on the same inputs.

MATLAB is a good second opinion here: it is a different language with a different optimisation solver. Agreement does not prove the physics is right, but disagreement would show a coding mistake.

Chapter 2 of 8

The battery model, the ACC and the MPC were rewritten; the rest was not

Three parts were written again in MATLAB: the BMW i3 battery model (with regen at efficiency 0.65 and 35 kW), the conventional ACC that follows the lead car, and the battery-aware MPC with a constant-speed preview. At every 0.5 s decision the MPC solves a small optimisation with quadprog, while the car moves in 0.1 s steps.

The map-aware MPC for speed breakers, the lead-car forecasters, SAC and safe SAC, the sliding-mode controller and the cut-in scenarios were not ported.

Chapter 3 of 8

These 10 are not the 160 windows of Run it. They are a separate small set made for this check.

Chapter 4 of 8

Website, MATLAB and Python agree to within 0.16%

The website and MATLAB give the same battery energy: the largest difference over the 10 windows is 0.000% for the ACC and 0.002% for the MPC, with 0 solver failures. The paper's Python differs from the website by up to 0.159% and from MATLAB by up to 0.159%, because its MPC solver (OSQP) stops at slightly different tolerances. The pre-registered rule was met (verdict PASS).

Chapter 6 of 8

Ridge, KNN and SVR match Python; the boosted trees differ because they are a different algorithm

The Train it page also fits power models on the BMW i3 data. The same fold-0 split, features and physics target were exported to MATLAB, which fitted its own versions with the Statistics and Machine Learning Toolbox.

Ridge and KNN match Python (difference in error: 0.00% and 0.00%), and SVR comes within 0.07%. Ridge had a pass rule written before the run (within 0.5%): it passes, in both modes. For boosted trees MATLAB has LSBoost, not LightGBM. They are different algorithms, so a gap is expected: MATLAB 3.687 kW against LightGBM 3.751 kW (−1.71%). This is not a failure, and the MATLAB model was not re-tuned.

Chapter 7 of 8

It shows the code agrees, not that the car model is right

  • Checked: the frozen BMW i3 physics with regen, the conventional ACC and the MPC with constant-speed preview, on 10 windows. The website matches MATLAB to 0.000% (ACC) and 0.002% (MPC).
  • Checked in the ML part: Ridge, KNN and SVR give the same error in MATLAB as in Python on the same data. The boosted-tree gap comes from different algorithms.
  • Not checked: the map-aware MPC, forecasts, SAC and safe SAC, the sliding-mode controller and the cut-in scenarios have no MATLAB port.
  • Same author, both versions. This finds slips in solver, indexing and units. It does not compare the physical model with a real car's measurements.
  • Different windows. The 10 windows come from the V2V test set, not the 160 windows of Run it.

Does show

  • Website and MATLAB agree on energy to under 0.1%
  • Ridge, KNN and SVR agree on the BMW i3 data

Does not show

  • That the battery model matches a real car
  • Anything about the controllers that were not ported
